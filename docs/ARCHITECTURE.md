# Architecture

## Request flow

```
browser (/static/app.js)
      |  fetch + Bearer access token
      v
SecurityHeaders -> RateLimit -> RequestContext -> TrustedHost -> CORS
      v
FastAPI router (/api/v1) -- Depends(require_role) --> handler
      v
services/planner.py  ---- ml/forecaster.py  ---- optimizer/{milp,greedy}.py
      v
SQLAlchemy async session -> SQLite (dev) | Postgres (prod)
```

Middleware order matters. Security headers are outermost so they are attached even to 429 and 413 responses generated by the layers beneath.

## Modules

| Module | Responsibility | Depends on |
|---|---|---|
| `app/config.py` | settings, production guards | — |
| `app/models.py` | ORM schema | — |
| `app/schemas.py` | strict I/O contracts | `security.passwords` (strength rule) |
| `app/security/` | hashing, JWT, middleware | `config` |
| `app/deps.py` | auth dependencies, RBAC | `security`, `db` |
| `app/ml/` | features, registry, forecaster | numpy, scikit-learn |
| `app/optimizer/` | labour rules, MILP, greedy | pulp |
| `app/services/planner.py` | DB → specs → forecast → solve → persist | `ml`, `optimizer`, `models` |
| `app/api/` | HTTP surface | everything above |

`ml/` and `optimizer/` import no web or database code. They take plain dataclasses and dicts, which is why they are testable without a running app and why either could be lifted into a worker process unchanged.

## Data model

```
User 1---* RefreshToken            (jti unique, family groups a session lineage)
Employee 1---* Availability        (unique per employee+weekday)
Employee 1---* TimeOff             (unique per employee+day)
ShiftTemplate                      (role, start_hour, end_hour, 3-10h span)
SalesRecord                        (unique per day+hour -> ingestion is idempotent)
Schedule 1---* Assignment          (unique per schedule+employee+day)
AuditLog                           (append only)
```

Two database-level uniqueness rules carry real invariants rather than hygiene: `sales_records(day, hour)` makes re-ingestion of a corrected day safe, and `assignments(schedule_id, employee_id, day)` makes the one-shift-per-day rule impossible to violate even if a future solver has a bug.

## Forecasting

Target: covers in a single service hour.

Features (13): hour, weekday, weekend flag, holiday flag, weather score, sin/cos of hour, sin/cos of weekday, `lag_168`, `lag_336`, four-week same-slot mean, four-week day-total mean.

Design rules:

1. **Lags are at least one week back.** A shorter lag would not be available when planning a rota several days ahead, so a model trained on it would be useless in production even though it would score well offline.
2. **Warmup is dropped.** The first 14 days have no valid lags; including them would train the model on default-filled features.
3. **The holdout is the last N days, not a random sample.** Random splits on time series leak future information into training and inflate metrics.
4. **Refit on everything after scoring.** Metrics come from the date-held-out fit; the deployed estimator sees all history.
5. **Multi-week horizons recurse.** Day 10's `lag_168` is day 3's prediction. Error compounds, which is why the API caps the horizon at 21 days.

The seasonal-naive fallback exists because a gradient-boosted model on 60 rows is worse than an average, and it is honest about it: the response carries `fallback: true` and `model: "seasonal_naive"`.

## Optimization

### Formulation

Sets: employees *E*, days *D*, templates *T*, service hours *H*, roles *R*.

Variables:
- `x[e,d,t] ∈ {0,1}` — created only when *e* is qualified for *t*'s role, is available for the whole span, and has no approved leave on *d*
- `u[d,h,r] ≥ 0` — understaffing slack
- `o[d,h,r] ≥ 0` — overstaffing slack
- `ot[e,w] ≥ 0` — overtime hours in week *w*
- `sf[e,w] ≥ 0` — contracted-hours shortfall

Objective:

```
min Σ x[e,d,t]·rate[e]·hours[t]
  + Σ ot[e,w]·rate[e]·0.5
  + P_under · Σ u
  + P_over  · Σ o
  + P_min   · Σ sf
```

Constraints:

```
C1  Σ_t x[e,d,t] ≤ 1                                   one shift per day
C2  (encoded in variable construction)                 qualification, availability, leave
C3  Σ_{d∈w,t} x[e,d,t]·hours[t] ≤ maxWeekly[e]         hour cap
C4  x[e,d,t1] + x[e,d+1,t2] ≤ 1  if rest(t1,t2) < R    daily rest
C5  Σ_{d∈window} x[e,d,·] ≤ k                          consecutive days
COV Σ x  + u[d,h,r] ≥ need[d,h,r]
    Σ x  - o[d,h,r] ≤ need[d,h,r]
```

### Why coverage is soft

With hard coverage, any week where demand exceeds the roster's legal capacity returns "infeasible" — no roster, no diagnosis. With penalised slack the solver returns the best legal roster it can build and reports the deficit in staff-hours, which converts directly into a hiring or hours decision. The demo dataset is deliberately capacity-short so this path is exercised rather than hypothetical.

### Penalty calibration

`understaff_penalty` (default 90) sits well above the highest hourly wage, so the solver always prefers paying someone over leaving an hour uncovered — including at overtime rates. `overstaff_penalty` (default 8) sits below wage, so a surplus hour is tolerated only when it is the byproduct of a shift block that covers a real gap. Move the ratio and the roster's character changes; both are per-request parameters, not constants.

### Complexity

Variable count is bounded by |E| × |D| × |T| after feasibility filtering — 369 for the 27-staff, 7-day, 9-template demo. Constraint count is dominated by the pairwise rest constraints, O(|E| × |D| × |T|²). CBC reaches optimality in about 1.6 s at that size. A 200-employee, 4-week instance should be run behind a job queue with the time limit raised; the API's `solver_time_limit_seconds` already caps the wait, and CBC returns its incumbent when the limit hits.

## Scaling notes

**Multi-replica.** Two components hold in-process state: the rate limiter and the login lockout counter. Move the limiter to Redis (`INCR` with `EXPIRE` on an IP+bucket key); lockout state already lives in the `users` table and is safe across replicas.

**Long solves.** Move `POST /schedules/optimize` to a task queue: persist a `Schedule` row in `queued`, return 202 with the id, run the solve in a worker, poll `GET /schedules/{id}`. `optimizer/` needs no changes for this — it is already free of web and database imports.

**Postgres.** Swap `RWO_DATABASE_URL` and install the `postgres` extra. One code change is required: `demand/ingest` uses the SQLite dialect's `on_conflict_do_update`; the Postgres dialect exposes the same API under `sqlalchemy.dialects.postgresql.insert`.

**Migrations.** The schema is currently created from metadata on startup, which is right for a demo and wrong for a system with production data. Alembic should land before the first breaking schema change.

## Testing strategy

Three layers:

1. **Unit** — password and token primitives, feature matrix shape and leakage guards, staffing policy bounds.
2. **Property-style solver tests** — every hard constraint is asserted against solver *output*, parametrised over both backends. These catch the failure mode that matters: a solver that returns a cheap but illegal roster.
3. **End-to-end HTTP** — ingest, train, forecast, optimize, summarise, publish through the real ASGI stack with real middleware.

The suite is fully offline: synthetic fixtures with fixed seeds, a throwaway SQLite file, no network. Argon2 parameters are lowered in the test environment only, so the security tests still exercise the real hasher without a minute of CPU burn.
